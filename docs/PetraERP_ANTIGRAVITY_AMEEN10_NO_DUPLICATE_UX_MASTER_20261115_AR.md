# PETRA ERP — ACCOUNTANT-FIRST UX / UI OVERHAUL
## البرومبت التنفيذي الشامل لـ Google Antigravity
**الإصدار:** منع التكرار + المطابقة الوظيفية للأمين 10 — 2026-11-15

**المشروع:** Petra ERP — محاسبة ومستودعات | **البيئة الحالية:** C# / .NET 10 / WPF / ASP.NET Core Web API / SQL Server | **المرجع الوظيفي:** الأمين ERP 10، مع تحسين تجربة الاستخدام لا نسخ شكله حرفيًا.

> **مهمتك هي إجراء تعديل حقيقي على المشروع الحالي بعد فحصه، لا توليد صور ولا تقديم تصور نظري فقط.** نقطة الفشل التي يجب إزالتها: المحاسب يضطر إلى الضغط على «إضافة سطر» في بعض السندات كلما أنهى السطر السابق، وتوجد شاشات وفواتير وسندات غير متسقة في التبويبات والحقول والأوامر. نريد نظام إدخال تجاريًا عمليًا، سريعًا، كثيف المعلومات، يعتمد على لوحة المفاتيح، واضحًا للمحاسب المتمرس والجديد، دون المساس بسلامة القيد والترحيل.


## -1) قاعدة الإحلال داخل المكان — أهم شرط في المهمة
**إيقاف فوري لأي تنفيذ يضيف نسختين من الوظيفة نفسها.** التحسين ليس صنع حزمة «PetraERP.Desktop.NewUI» ولا إضافة `VouchersViewV2.xaml` ثم إبقاء القائمة الرئيسية تفتح القديم. المطلوب تطوير `VouchersView.xaml` وViewModel ومساراتهما الأصليين، أو تحويل مكون داخلي مشترك إلى مكوّن محسّن **داخل الشاشة الأصلية**؛ إن احتاج تغييرًا بنيويًا جذريًا فاستبدل التنفيذ القديم مع تحديث مساره ومراجعة كامل مستدعِيه، ولا تترك نسختين صالحتين للإنتاج.

### معمارية شاشة واحدة لكل وظيفة (Single Screen Ownership)
1. قبل أي كتابة، استخرج جدولًا آليًا من `MenuRegistry.cs`, `NavigationService`, `DesktopViewModel`, `DesktopShortcutRouter`, `MdiWorkspaceHost`, `DesktopWindow`, Command Palette, Quick Actions, Recent/Favorites, Context Menus ومن كل `UserControl` وViewModel؛ الجدول: `FeatureId | RouteId | MenuId | View XAML | ViewModel | Factory/DI | EntryPoints | Permissions | Client/API | Tests`.
2. اجعل `MenuRegistry` و`NavigationService.Routes` مصادر الحقيقة الموجودة **بدل** إنشاء Registry ثانية. لكل `FeatureId` يجب أن يكون هناك مسار وظيفي واحد واضح يفتح **الشاشة المعتمدة نفسها** من القائمة الرئيسية، لوحة البحث، اختصارات الكيبورد، شجرة الأدلة، نتائج التقارير والروابط بين المستندات.
3. إذا كانت هناك شاشتان بحق لوظيفتين محاسبيتين مختلفتين، فلا تدمجهما لمجرد التشابه: `daily-vouchers` سند يومية، `journals` قيود يومية/دفتر، `treasury-vouchers` قبض ودفع، `sales-invoices` فواتير مبيعات، `purchase-invoices` مشتريات. كل منها يحتفظ بعقده المالي ويشارك عناصر UI فقط.
4. ممنوع: `*V2.xaml`, `*NewView.xaml`, `LegacyView` معلقة بالإنتاج، قوائم منسوخة، نوعان من `DocumentCommandBar`, شاشة جديدة وراء `ShowDialog` فوق القديمة بلا داعٍ، مكونات حُشرت في `Grid` بينما بقيت القديمة Hidden؛ الأداة الوحيدة المسموحة كنافذة فرعية هي **الاختيار السياقي أو الإعداد/التقرير/التأكيد** عندما يكون لها غرض مستقل وتعود بمخرجات واضحة إلى النافذة الأم.
5. عند الحاجة لتغيير View أو ViewModel جذريًا: اعمل داخل نفس المسار، حافظ على binding contracts حيث أمكن، واستخدم refactor تدريجيًا مع حذف الأسطر القديمة غير المستعملة **بعد** اختبارات التنقل والعكس وصلاحيات المستخدم. لا تحذف كودًا له مستدعٍ أو حاجة قبل إثبات استبداله؛ ولا تُسقط وظائف نافذة أثناء توحيد شكلها.
6. لا تكرر التعريفات بين `Themes` وشاشات البيع والشراء؛ استخرج الأنماط المكررة إلى ResourceDictionaries مشتركة ثم حدّث الشاشتين، مع اختبارات مظهر وعدم تضارب مفاتيح الموارد.
7. أضف اختبارات آلية تفشل عند وجود Route مكرر، `MenuId` يشير لشاشة مهجورة، ViewModel مفقود من DI، EntryPoint يفتح نافذة غير معتمدة، اختصار يستدعي أمرًا مختلفًا، أو عنصر تحكم جديد غير مستخدم بينما القديم باقٍ في النوافذ.
8. قبل كل Commit: `git diff --name-status`, فحص المراجع `rg`, ثم تدقيق `NoDuplicateWindows` وتوثيق `ReplacedInPlace/RemovedObsolete/RetainedBecauseDistinct`. ممنوع اعتماد أي مرحلة إذا كانت صفحة جديدة معروضة فوق نظيرتها القديمة أو اختفت وظيفة من القائمة.
9. **لا تسمِّ العمل «إعادة تصميم» عندما يكون مجرد تنسيق ألوان:** أعِد بناء سلوك الإدخال وربط الحقول والأوامر والتعامل مع الأخطاء في الشاشات الحقيقية، بنفس صلاحيات العمل ودورة المستند المحاسبية.

### اختبار عدم الازدواج (معيار رفض صريح)
فتح «سند قبض» من 4 طرق: القائمة العليا، البحث السريع، الاختصار، وروابط الطرف. النتيجة المطلوبة: نفس `RouteId`, نفس ViewModel lifecycle, نفس حفظ/ترحيل/طباعة/تحذيرات المسودة، ونافذة واحدة نشطة للمستند نفسه، أو تجلب النافذة الموجودة للأمام بدل إنشاء نسخة مكررة. كرر للمبيعات والمشتريات والقيود والتقارير. إذا فشل أحد الطرق: **Gate FAIL**.

## 0) مهم جدًا — قواعد غير قابلة للتفاوض
1. اقرأ الشيفرة **الفعلية** أولًا، وافحص XAML وViewModels وControls وCommands وDTOs والـAPI والاختبارات. لا تستنتج أن ميزة ناقصة من مظهرها فقط؛ بعضها موجود أصلًا في بعض النوافذ.
2. حافظ على قاعدة البيانات، قواعد الترحيل، الأرصدة، دورة الموافقة/الترحيل/العكس، تعدد الشركات والسنوات، والصلاحيات. لا تعدل خدمة مالية لإصلاح شكل نافذة دون عقد قبول واختبارات تغطي الأثر.
3. لا تستبدل WPF بـ Electron أو WebView أو Flutter، ولا تعِد بناء الواجهة من الصفر، ولا تُنشئ طبقة ثانية من مكونات قائمة بالفعل؛ طوّر الموجود.
4. التصميم **Accountant-first**, وليس Dashboard-first ولا بطاقات ضخمة أو قوائم أزرار مزدحمة. شاشة المستند هي مكان عمل المحاسب الأساسي.
5. كل سطر إدخال جديد يجب أن يكون قابلًا للإدخال فورًا **دون نقرة «إضافة سطر»**. عرض 50 خانة سطر منطقيًا كافتراضي (قابل للضبط)، بينما تعرض النافذة من هذه الأسطر ما يسعه ارتفاعها مع تمرير افتراضي مفعّل.
6. **الصفوف الفارغة للعرض فقط:** لا ترسل 50 صفًا فارغًا للـAPI ولا تحفظها في SQL. خزّن فقط الصفوف المكتملة. أما الصف الذي بدأ المستخدم إدخاله ولم يكمله فلابد من تنبيه سياقي محدد بالصف والخانة، لا تجاهله.
7. لا تخلط بين سند قيد GL، سند يومية، سند قبض نقدي، سند دفع، سند دفع موزع، سند ربط/تسوية الذمم؛ قد تتشابه الواجهة لكن **العقود والحركات المحاسبية تختلف**. إذا كان backend لا يدعم مجموعة من الأسطر لنوع سند، لا تتظاهر بدعمه: استخرج النقص وأضف دعمًا صريحًا وآمنًا فقط بعد توثيق ومعالجة API وقواعد الحساب والاختبارات. أبقِ وضع السند الفردي سريعًا لمن يحتاجه.
8. لا تقل «تم» إلا بعد تشغيل البناء والاختبارات وعرض الصور الفعلية للشاشات في نسخة Windows، مع قائمة الملفات المتغيرة وقياسات قبل/بعد. إذا كانت بيئة التشغيل لا تسمح بإجراء اختبار، اذكر ذلك كفجوة ولا تصنّفه PASS.
9. أرقام العرض غربية 0–9، واجهات RTL، مع إمكانية ضبط فواصل تجميع الأرقام **كل ثلاثة أو كل رقمين** بشكل منفصل عن عدد المنازل العشرية. لا تحوّل الأرقام إلى هندية.
10. دعم الموديولات المستقبلية ضروري: أي موديول مثل الأصول والرواتب والموظفين يجب أن يتمكن من استخدام نفس منظومة الشاشات والبحث والاختصارات والمستندات والتقارير عبر عقود مشتركة مستقرة، دون الاعتماد على كود المبيعات.

## 3) تصميم موحد — Petra Accountant Pro
- حافظ على سطح العمل متعدد النوافذ MDI / الشريط العلوي أفقيًا الخاص بنواة Petra، مع شريط الحالة باسم الشركة، قاعدة السنة، الفرع، المستخدم، واتصال API.
- الهيكل الافتراضي لكل مستند: **عنوان ورقم وحالة**؛ **شريط أوامر مختصر**؛ **رأس مضغوط 2–3 أسطر**؛ **شبكة إدخال هي المساحة الأكبر (55–70% من ارتفاع منطقة المحتوى عند توفر المساحة)**؛ **شريط مجاميع ثابت**؛ **أوامر طباعة/معاينة/حفظ/جديد** واضحة؛ خيارات متقدمة قابلة للطي.

- **رأس مستند لا يزاحم الشبكة:** رقم، التاريخ، الطرف، المستودع أو الحساب المالي، طريقة الدفع، العملة/التعادل، الفرع والنمط؛ الخيارات قليلة الاستخدام في «تفاصيل إضافية» بدل احتلال 50% من النافذة.
- اجعل الأوامر الأساسية (جديد، حفظ، تعديل، اعتماد، ترحيل، معاينة، طباعة) مرئية بحسب حالة المستند والصلاحيات؛ الأوامر الثانوية في «المزيد» مع السبب عند تعطيل أمر محظور، وليس أزرارًا صامتة. مع حماية تغييرات غير محفوظة.
- التنقل بين مستندات سابق/التالي/أول/آخر في مكان ثابت؛ لا تخلط بين تنقل مستندات وتقليب صفحات قائمة السجلات.
- عند تغيير الحجم حافظ على موقع آخر خلية تمت كتابتها، وارتفاع الشبكة وحجم الأعمدة والنافذة؛ لا تُعد إنشاء الـViewModel أو تحميل كامل القوائم لمجرد تغيير الحجم.

## 4) محرك إدخال الأسطر الموحد — أعلى أولوية
أنشئ/طوّر عنصرًا عامًا `PetraDocumentEntryGrid` مبنيًا على `PetraAccountingDataGrid` و`GridEntry` الموجودين، أو واجهة/Behavior مشتركة، **لا نسخة جديدة مستقلة غير متصلة**.

متطلبات السلوك:
1. عند فتح مستند جديد يظهر **50 صفًا منطقيًا جاهزًا للإدخال** تلقائيًا (إعداد عام يمكن تغييره للمستخدم/نوع المستند). قد يرى المستخدم 8–20 صفًا بحسب حجم النافذة؛ يظل الانتقال إلى بقية الصفوف بالتمرير تلقائيًا.
2. عند النزول إلى آخر صف مستخدم، جهز صفوفًا إضافية تلقائيًا في دفعات 10–25 عند الحاجة، مع سقف آمن قابل للضبط يمنع استهلاك الذاكرة بلا حد. لا تجعل إنشاء الصف التالي مشروطًا بالنقر على «إضافة سطر».
3. صف واحد مكوّن من عناصر مناسبة لهذا المستند. `Enter` ينهي تحرير الخلية وينتقل إلى **الحقل التالي بحسب خريطة تنقل محددة**، وإذا كان الأخير ينتقل إلى أول حقل بالسطر التالي. `Tab` يتبع مسارًا مفهومًا، و`Shift+Tab` للخلف. توحيد السلوك وعدم انتقال التركيز إلى أزرار الشاشة أثناء إدخال صف.
4. `F3` أو مفتاح `*` في حقول المراجع يفتح نافذة الاختيار، بشرط ألا يمنع كتابة الرمز `*` في سياقات النص العادي عند الحاجة. في عنصر البحث نفسه، اكتب أول حرفين لاقتراح النتائج، الأسهم للتحديد، `Enter` للاختيار، `Esc` للإغلاق والعودة لنفس الخلية. دعم البحث بالرمز، الاسم، الاسم الجزئي، والباركود للمواد.
5. `Insert` ينتقل إلى أول صف فارغ جاهز أو يدرج صفًا إذا كان المستخدم يقصد ذلك. `Ctrl+Delete` يحذف السطر المحدد بعد حماية البيانات المدخلة؛ `Ctrl+Z/Y` للتراجع/الإعادة محليًا قدر الإمكان؛ `F2` تحرير خلية؛ `Ctrl+S` حفظ؛ `Ctrl+N` جديد؛ `Ctrl+P` طباعة؛ `Esc` يغلق القائمة أولًا ثم تحرير الخلية ثم النافذة وفق سياق واضح. راعِ توافق الاختصارات الحالية واسمح بتخصيصها.
6. دعم نسخ/لصق Excel / TSV متعدد الخلايا وفق تحقق النوع والعملة والتواريخ، دون إدخال أي قيم في حقول غير متوافقة، مع كشف خطأ على مستوى كل خلية.
7. نسخ قيمة الخلية من الصف السابق واستخدام آخر وصف أو مركز كلفة عندما يناسب طبيعة المستند؛ لا تورّث حسابًا أو مبلغًا ماليًا تلقائيًا بطريقة غير آمنة.
8. ألوان متناوبة خفيفة، رقم الصف ظاهر دائمًا، خلية التحرير لها إطار واضح، واجهة RTL لكن الأرقام والمحارف اللاتينية تعامل باتجاه مناسب. عمود البيان يتسع للنص ويقع مباشرة بعد السعر في الفاتورة كما طلب المستخدم؛ لا تجعله مخفيًا خلف شريط تمرير دون داعٍ.
9. لا تحفظ `PristineBlank`، وتجاهل السطر الفارغ تمامًا في التحقق وDTO؛ **السطر الجزئي لا يُتجاهَل**، بل يُظهر سببًا محددًا ويحافظ على التركيز في الخلية الخاطئة. لا تضِف صفوفًا إلى جدول SQL إلا عند وجود بيانات فعلية كاملة.
10. لا يحدث أي طلب API عند كل Tab أو Enter أو تعديل سعر/كمية؛ الحساب المحلي للصف والمجاميع يتم فورًا. استدعاء API للبحث فقط عند الحاجة مع Debounce وCancellationToken وكاش Workspace-scoped وإلغاء الردود القديمة.
11. بعد حفظ المستند لا تمحُه فجأة إذا فشلت استجابة الشبكة. اعرض نتيجة واضحة وراجع Idempotency الموجود؛ لا تنشئ مستندًا مكررًا بإعادة المحاولة العمياء.

## 5) سند قيد GL — واجهة واحدة قوية
- رأس: رقم السند، التاريخ، تاريخ الترحيل إن لزم، العملة والتعادل، الفرع، البيان، مركز الكلفة الافتراضي، منشئ/حالة السند.
- جدول عريض: `رقم السطر | الحساب | الزبون/المورد المشروط | البيان | مدين | دائن | مركز الكلفة | عملة السطر/التعادل عند الحاجة`. يسمح تخصيص ترتيب وإظهار الأعمدة الإضافية.
- عند اختيار الحساب تملأ المعلومات المرتبطة المسموح بها تلقائيًا، ولا يُجبر المستخدم على اختيار زبون إن لم يكن الحساب يتطلب ذلك. عند اختيار طرف مرتبط بالحساب تحقّق من الربط داخل نفس الشركة والسنة.
- تمنع كتابة مبلغ مدين ودائن موجبين في السطر ذاته بحسب قاعدة العمل، وتمنع ترحيل قيد غير متوازن. شريط المجاميع المباشر: مجموع المدين ومجموع الدائن والفرق، والفرق = صفر عند التوازن. السماح بحفظ مسودة ناقصة إذا كان backend يسمح؛ منع الترحيل فقط عند خطأ محاسبي.
- فتح القيد الناتج من فاتورة أو سند عبر «فتح الأصل» أو «الانتقال للمصدر»، دون تعديل القيد المرحّل مباشرة.
- افصل عرض بيانات السند عن التدقيق والصلاحيات وإجراءات الترحيل؛ حافظ على خصائص multi-currency وIdempotency وrow-version.

## 6) سند يومية — أوقف مشكلة السطر الواحد نهائيًا
- افحص `DailyVoucherViewModel.ResetRows()` و`AddRow()`؛ استبدل إعادة تعيين صف واحد بسجل صفوف جاهزة 50 في كل سند جديد/بعد الإلغاء/بعد التحميل للتحرير، مع المحافظة على الأسطر المكتملة الموجودة.
- لا تضع 50 صفًا فارغًا في payload. اعرض 50 كحد افتراضي، ولو كانت 8 فقط مرئية؛ حساب مجاميع مدين/دائن والرصيد الفوري.
- الحساب الرئيسي/الصندوق في الأعلى، وأسطر الأطراف والحركات في الجدول. اضبط أسماء الأعمدة وفق معنى `Pay` و`Receive` الحقيقي في DTO ولا تبدّل المدين والدائن بسبب RTL فقط.
- اختبر إدخال سند 1 و10 و50 و75 سطرًا دون الضغط على «إضافة»، وفتح سند قديم وإضافة سطر وتعديل وحذف سطر وحفظه مع تطابق القيود.

## 7) سند قبض ودفع — اعمل حسب النوع المحاسبي
- صورة الأمين المرجعية تعرض رأسًا فيه حساب الصندوق/البنك وتاريخ وعملة ورصيد سابق، وجدولاً متعدد الصفوف للأطراف والمبالغ وبيان ومركز كلفة، ورصيدًا نهائيًا. نفّذ هذا الشكل الوظيفي **عندما يدعم عقد المستند تعدد البنود**.
- في Petra يوجد أصلًا `LineRows` و`EnsureDistributionBuffer(50)` لمسار `IsDistributionPayment`. عمّم تجارب الشبكة والاختصارات والمجاميع على هذا المسار أولًا؛ أصلح حالات إخفاء شبكة التوزيع أو مسح صفوفها عند اختيار `DraftPartyId` بطريقة مربكة.
- سند قبض/دفع لطرف واحد يجب أن يبقى إدخاله بسيطًا دون فرض 50 حقلًا يجب تعبئتها. اجعل الإدخال «سريع (طرف واحد)» و«موزّع (عدة أطراف/حسابات)» بحسب السياسات المعتمدة، باستخدام تخطيط موحد. إذا لم يدعم backend القبض متعدد البنود فلا تُظهر وضعًا وظيفيًا كاذبًا؛ نفّذ Backend Gap رسميًا مع معاملة ذرية وتوليد GL صحيح، أو سجّل الفجوة بوضوح إلى حين إنجازها.
- لا تخلط تخصيص قبض الفواتير/تسوية الذمم `AllocationRows` مع أسطر أطراف السند `LineRows`؛ الأول يستند إلى فواتير قائمة ويحتاج مطابقة إجمالي وتسجيل تسوية، والثاني تخصيص عمليات دفع/قبض بين حسابات/أطراف.
- يجب أن يكون مبلغ الرأس متزامنًا مع مجموع التفاصيل وفق سياسة المستند، مع حالة واضحة إذا كان المستخدم قد أدخل المبلغ يدويًا. لا تغيّر المبلغ بصمت بعد تعديل الأسطر.
- إظهار الرصيد السابق واللاحق للصندوق أو الحساب حيث تسمح الصلاحيات؛ لا تُجرِ استعلام رصيد عند كل ضغطة زر.

## 8) فواتير المبيعات والمشتريات والمرتجعات
- رأس مدمج: نمط، رقم، تاريخ، عميل/مورد، طريقة الدفع، المستودع، العملة/سعر الصرف، الفرع، البائع عند الحاجة، وبيان عام.
- **50 سطرًا جاهزًا** بنفس محرك الشبكة، أول خلية المادة؛ اختيارها بالاسم/الرمز/الباركود، الوحدة المناسبة ثم الكمية فالسعر ثم البيان فالحسم/الضرائب حسب النمط، والإجمالي للقراءة.
- **البيان بعد السعر مباشرة** في الترتيب الافتراضي. يختار المستخدم الأعمدة الظاهرة وترتيبها وحفظه حسب الشركة/نوع الفاتورة/المستخدم، دون تغيير الحقول المفروضة لأسباب ضريبية أو نظامية.
- اعتماد آخر أسعار بيع/شراء وشروط الدفع ووحدات المادة وربط المخزون وفق السياسات الموجودة فعليًا. عرض سعر آخر شراء والوسطي في قائمة مناسبة عندما تسمح الصلاحية؛ لا تكشف سعر التكلفة لمستخدم غير مخوّل.
- تحذير كمية غير منطقية (مثل >100) **قابل للضبط حسب المادة/الوحدة** لا حظر عام، مع استثناء مسموح وفق الصلاحية. منع الكميات السالبة فقط وفق خيارات النظام مع رسالة مفهومة.
- أسفل شبكة المواد: قسم مضغوط للحسميات والإضافات عند الحاجة، وشريط مجاميع مثبت مع الإجمالي والحسم/الإضافة والضريبة والصافي. لا يتقلص الجدول لصالح تفاصيل قليلة الاستخدام.
- فصل واجهات المرتجع عن الفاتورة الأصلية محاسبيًا، مع المحافظة على رابط الأصل والتحقق من الكميات الممكن إرجاعها وعدم تكرار المرتجع.
- بعد حفظ فاتورة مبيعات يمكن فتح القيد الناتج، حركة المستودع، كشف الطرف، سجل الترحيل، والطباعة من قائمة سياقية أو أوامر واضحة حسب الصلاحية.

## 9) شاشات الجرد والمناقلات وحركات المستودعات
- طبق نفس محرك 50 صفًا مع أعمدة صحيحة لكل حركة: المادة، وحدة، كمية، مصدر/وجهة عند الحاجة، البيان، التكلفة إن كانت مسموحة.
- حركات المناقلة تتطلب فحص المستودع المصدر والوجهة وصحة المخزون وفق سياسات السماح بالسالب؛ تأكد ألا يتحول تحسين الإدخال إلى طلب API لكل سطر.
- الجرد: كميات دفترية للقراءة وكميات فعلية قابلة للإدخال، الفرق محسوب، مع فرز وتصفية، ومسار مراجعة قبل ترحيل فرق الجرد.

## 10) مكونات البحث والاختيار والقوائم المنبثقة
- على **كل حقل مرجعي** من دليل الحسابات والمواد والعملاء والموردين والمستودعات والعملات ومراكز الكلفة والفروع والأنماط: زر بحث مرئي، واختصار موحد F3 أو `*` في سياقه الصحيح، وقائمة منبثقة تظهر أيضًا إذا ضغط المستخدم مفتاح الاختصار على حقل قابل للبحث.
- أداة `LookupPicker` واحدة مدعومة بـ AsyncSearchProvider؛ البحث بأول حرفين، قائمة نتائج فيها رمز/اسم/تفاصيل موجزة، اختيار بالأسهم ثم Enter، إغلاق Esc، قائمة السياق بالزر الأيمن، فتح بطاقة العنصر عند السماح.
- لا تُلغِ اختيار القيمة الصحيحة عندما يكتب المستخدم جزءًا من الاسم؛ لا تعرض «عبّئ كذا أولًا» إذا أمكن استنتاج القيمة من النمط أو الطرف أو المستودع. اعرض سبب المتطلب وحدد الحقل تلقائيًا عندما يكون إلزاميًا.
- تصفية الخيارات المنبثقة بالـWorkspace والفرع والدور، وإلغاء الكاش فور تغيّر صلاحيات أو قاعدة السنة. لا تعرض حسابات غير قابلة للحركة ضمن قوائم اختيار حساب القيد إلا إذا كانت سياسة القيد تسمح بذلك.

## 11) البطاقات والأدلة والنوافذ المرجعية
- دليل الحسابات والمواد: أب/أبناء، شجرة منظمة، بحث فوري، عرض تفاصيل العنصر المحدد، قائمة زر يمين (جديد، تعديل، حذف عند الجواز، فتح، كشف حساب/حركة المادة)، لا تجمد كامل الواجهة على آلاف السجلات.
- بطاقات الحساب والزبون والمورد والمادة والمستودع والفرع والعملة ومركز الكلفة: رأس مختصر، تبويبات منظمة للبيانات المتقدمة، أزرار ثابتة، إمكانية فتح البطاقة من حقل البحث ثم الرجوع إلى نفس فاتورة الإدخال دون ضياع البيانات.
- النوافذ المنبثقة ليست حوارات ملء الشاشة عشوائية؛ اضبط نسب الأحجام، أولوية التركيز، قواعد Modal/Modeless، نافذة عدم حفظ التغييرات، ومكان الظهور من دون تغطية الخلية التي يعمل بها المحاسب إن أمكن.
- حافظ على MDI وفتح نافذتين أو أكثر لشركتين/سنتين مع إظهار Workspace واضح لكل نافذة لمنع إدخال قيد في السنة الخطأ.

## 12) التقارير والمعاينة والطباعة من الواجهة
- ضع نافذة معلمات تقرير موحدة: من تاريخ/إلى تاريخ، الحسابات/المواد/الأطراف/الفرع/مركز الكلفة، خيارات «يتضمن في البيان»، حفظ آخر شروط لكل مستخدم وWorkspace.
- نافذة نتائج احترافية فيها مجموعات/مجاميع، تثبيت رؤوس الأعمدة، بحث وتصفية وفرز، انتقال من الحركة إلى المستند الأصلي، وصفحات/Keyset للبيانات الكبيرة.
- واجهة المعاينة قبل الطباعة تعرض الترويسة والتذييل والشعار والفترة والعملة ورقم الصفحة والمجموع، مع تصدير PDF/Excel وطباعة سليمة RTL. لا تغيّر نتيجة التقرير المحاسبية لأجل الشكل، ولا تُحمّل 100 ألف صف في الذاكرة لمجرد فتح المعاينة.
- راعِ أن شاشة «ميزان المراجعة المصنف» في مراجع الأمين ليست نسخة بالضرورة من ميزان المراجعة العادي؛ لا تنقل حقولًا من نوع تقرير إلى آخر دون سند وظيفي.

## 13) نظام أنماط المستندات / تخصيص الحقول
- عرّف إعدادات `DocumentEntryProfile` مرنة بالنوع/النمط/الشركة/المستخدم: ترتيب الأعمدة، المخفي منها، العرض، الحقول المطلوبة بحسب السياسة، عدد الصفوف الافتراضية 50، اختصارات الإدخال، قفز الخانات المحسوبة، عرض الرصيد، ألوان الجدول، وضع حفظ/فتح مستند جديد.
- اجعل **إعدادات التخطيط منفصلة عن قواعد المحاسبة**؛ لا يمكن للمستخدم إخفاء حقل ضريبي إلزامي أو تجاوز شرط محاسبي بمجرد تغيير التصميم.
- Migration آمنة للإعدادات القديمة + قيمة افتراضية عند غيابها. تحقق من توافق المعايير عند تثبيت موديول جديد.

## 14) السلامة والأداء أثناء تعديل UX
- لا polling غير ضروري، ولا HTTP لكل ضغطة مفتاح أو تعديل خلية أو تحديث مجموع. قلّل الشبكة بإحضار Reference Bootstrap مخزّن حسب الشركة/السنة/الفرع/الصلاحية مع invalidation واضح.
- لا تستخدم `.Result` / `.Wait()` أو SQL في UI thread. استخدم async/await وCancellationToken للبحث، و`ICollectionView` وWPF virtualization الصحيحة مع اختبار عدم تلف الصفوف عند إعادة تدوير الحاويات `Recycling`.
- لا تلغِ حفظ المسودة أو القيد الحالي عند انقطاع API، لا تعيد `Save` عند timeout إلا بهوية Idempotency الصحيحة، وحافظ على ExpectedVersion/ETag والتعارضات التي تم إصلاحها سابقًا.
- بعد اختيار مادة أو حساب، حساب الإجمالي محليًا دون انتظار API (متى كانت القيم المرجعية كافية). يجب ألا تفقد الخلية التركيز بسبب PropertyChanged يحدّث الشاشة بالكامل.
- أضف قياسات قبل/بعد: زمن فتح نافذة على LAN؛ زمن ظهور اقتراح البحث؛ زمن تبديل 50 سطرًا بالكيبورد؛ عدد طلبات API عند فتح الشاشة وعند تحرير 20 سطرًا؛ تخصيصات الذاكرة؛ زمن حفظ/ترحيل؛ حالات التعارض. استهدف إحساسًا فوريًا دون نشر عتبات غير قابلة للقياس أو وعد غير واقعي بزمن خادم محدد.
- لا تكسر التزامن أو وحدة المعاملة أو سياسة الصلاحيات بغرض تحسين «الشعور بالسرعة». أي Backend Change يلزمه Unit + Integration + Concurrency.

## 15) الاختبارات العملية المطلوبة — ليست لقطات فقط
**سيناريو المحاسب الأول:** افتح سند يومية جديدًا، انتقل مباشرة إلى السطر الأول، أدخل 20 حركة بالكيبورد دون ضغط Add Row أو استخدام الماوس، راجع الإجماليات، واحفظ؛ أعد فتحه وتحقق من 20 حركة في DB لا 50 صفًا فارغًا.

**سيناريو المحاسب الثاني:** افتح سند قيد من عدة أطراف، أدخل 75 سطرًا، جرّب حسابًا فيه طرف مرتبط وآخر بلا طرف، وجرّب عدم توازن المبالغ ثم إصلاحه. لا يُرحّل غير المتوازن؛ الأرقام صحيحة.

**سيناريو المحاسب الثالث:** فاتورة 50 مادة: ابحث بالرمز والحرفين وF3، اختر المادة، كمية، سعر، بيان، حسم، وواصل Enter من سطر لسطر؛ لا تضغط «إضافة سطر» أبدًا. جرب نسخ 10 صفوف TSV من Excel، ثم احفظ وتحقق من النتيجة في المخزون والقيد.

**سيناريو المحاسب الرابع:** سند قبض لطرف واحد لا يطلب إجراءات غير مبررة، ثم سند دفع موزع على 10 حسابات، ثم مطابقة فواتير متعددة؛ تأكد من عدم خلط مخصصات الفواتير مع أسطر الحسابات.

**سيناريو المحاسب الخامس:** غيّر Workspace من 2025 إلى 2026 أثناء فتح نافذة أخرى؛ لا تظهر أي مادة/حساب من سنة خاطئة في البحث أو الكاش؛ تحقق من الصلاحيات.

**سيناريو المحاسب السادس:** افتح فاتورة سابقة مع تعديل مسموح، أضف صفًا، غيّر الكمية، اطبع، ثم اختبر مسودة غير محفوظة وانقطاع API دون فقدان المدخلات أو تكرار المستند.

**سيناريو المحاسب السابع:** شغّل الشاشات بأبعاد 1366×768 و1920×1080 و125%/150% DPI؛ لا قص ولا اختفاء أزرار ولا حقول نص بعرض ضيق؛ اختبر keyboard-only والتنقل العكسي.

**سيناريو المحاسب الثامن:** تحقّق من قارئ الشاشة/AutomationProperties/FocusVisibility بالقدر الممكن، واختبر Arabic RTL مع كتابة رموز المواد والأرقام الإنجليزية والأسعار وقواعد فاصل التجميع.

أنشئ اختبارات automated لـ `GridEntry` و`LookupPicker` و`DocumentEntryProfile` و`BlankSlotFiltering` و`PartialRowValidation` و`FocusNavigation`، واختبارات UI Automation أو FlaUI لتدفقات المحاسب، واختبارات API/SQL لوظائف السندات التي جرى تغيير عقودها. لا تعد نجاح BUILD دليل نجاح UX.

## 16) مراحل التنفيذ المرتبة
**Gate UX-0 (توثيق وBaseline):** Inventory لكل شاشة + صور حالية + مخطط إدخال + Test Plan + تحديد ما هو موجود فعلًا. لا تغيير بيانات.

**Gate UX-1 (المكونات المشتركة):** إصلاح `PetraAccountingDataGrid`, `GridEntry`, `LookupPicker`, الصفوف الفارغة، مفاتيح التنقل، أوامر التعديل، التصميم المشترك. اختبارات بالمكونات المعزولة.

**Gate UX-2 (أولوية أزمة السندات):** `DailyVoucher` أولًا، ثم `Journal`، ثم `Vouchers` مع التفريق بين قبض/دفع فردي وموزع. اعرض شاشة فعلية قبل/بعد وسيناريو 20/50/75 سطرًا.

**Gate UX-3 (الفواتير):** مبيعات، مشتريات، مرتجعات، مع شبكة المواد والوحدات/الأسعار والبيان بعد السعر والمجاميع، ثم تناسق طباعة المستند.

**Gate UX-4 (المستودعات والبطاقات):** الإدخال المتتابع في الجرد والمناقلات، وتحسين الأدلة والبطاقات والنوافذ المنبثقة.

**Gate UX-5 (التقارير والطباعة):** مرشحات وتقارير وPreview/PDF/Excel، مع الحفاظ على SQL/مقارنات الأرصدة.

**Gate UX-6 (اعتماد واستعداد الموديولات):** عقود UI SDK مشتركة لموديول الأصول/الموارد البشرية/الرواتب؛ وثائق دمج الموديول واختبارات توافق، ثم Smoke + UX + LAN + Regression واستقرار 3 جلسات متعددة.

**لا تنتقل إلى Gate تالية عند فشل اختبار مالي أو وجود فقدان تركيز أو تعذر الإدخال بدون الماوس في الشاشة التي أُغلقت.**

## 17) ما الذي تسلّمه في نهاية كل Gate؟
- قائمة دقيقة `ChangedFiles`, `UnchangedContracts`, `BackendImpact`, `DBImpact`, `MigrationImpact`.
- لقطتا شاشة **حقيقيتان** Windows لكل نافذة قبل وبعد، وليستا mockup مولّدًا.
- تسجيل قصير أو خطوات قابلة للإعادة لاختبار 20 سطرًا من لوحة المفاتيح، ونتيجة السجلات المخزنة.
- ملف `docs/UX_REDESIGN/PROGRESS.md` بحالات PASS/FAIL/BLOCKED لكل سيناريو وتبرير واضح.
- قياسات API وUI قبل/بعد تحت نفس الظروف، وعدد SQL/طلبات البحث، والذاكرة.
- قائمة الأعطال التي لم تُحل وأثرها على المستخدم، دون ادعاء تنفيذ ما لم يُختبر.

## 18) معايير القبول النهائية
**مرفوض** أن يُجبر المحاسب على Add Row بعد كل سطر؛ أو أن يضطر للماوس لاختيار كل حساب/مادة؛ أو أن تطلب النافذة حقولًا غير متعلقة بنوع المستند؛ أو أن تخفي الأخطاء وتكتفي بتعطيل الأزرار؛ أو أن تختلف خريطة Enter/Tab عشوائيًا بين المبيعات والمشتريات والسندات؛ أو أن يعرض البرنامج صفوفًا جاهزة ثم يخزنها كعمليات مالية فارغة.

**مقبول** فقط عندما تعمل الشاشات الحقيقية على Windows بالأرقام الغربية وRTL، وتبدأ مستندات الإدخال الجدولي بـ50 صفًا جاهزًا، وتدعم الاستمرار إلى أكثر منها تلقائيًا، مع مجاميع صحيحة وحفظ/اعتماد/ترحيل مطابق، وقائمة بحث وKeyboard-first، وشكل موحد، واختبارات نجاح مثبتة.

## 19) أمر البداية الآن
**ابدأ فورًا بمراجعة ملفات UX الواقعية ومراجع الأمين، ثم نفّذ Gate UX-0 مع مصفوفة Single Screen Ownership وNoDuplicateWindows قبل أي تعديل، وبعدها UX-1 وUX-2. لا تكتفِ بإخراج تصميم أو اقتراح. إذا وجدت عقد API يحد من دعم القبض/الدفع متعدد الصفوف فصنّفه بدقة، وأصلح ما يمكن فعليًا في الشبكة دون تزوير الدعم الخلفي. أعطني تقرير أول نتيجة مع شاشات Windows ومخرجات اختبارات.**
