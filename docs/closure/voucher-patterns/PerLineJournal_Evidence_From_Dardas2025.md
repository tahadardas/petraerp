# قيد لكل سطر: دليل من بيانات الأمين الفعلية (دردس 2025)

المصدر: قاعدة `AlAmeen_Dardas_2025` (محمّلة من `legacy-data/DB_2025` بالقراءة فقط). الاستعلامات للقراءة فقط.

## النتائج المقيسة
| القياس | النتيجة |
|---|---|
| قيود الفواتير (er000.ParentType=2) | 3290 فاتورة ← 3290 قيداً (قيد واحد لكل فاتورة، لا استثناء) |
| قيود الأوراق/السندات (ParentType=4) | 841 مستنداً ← 841 قيداً، حتى 156 سطراً في القيد الواحد |
| قيد مرتبط بأكثر من مستند | 0 |
| قيود يدوية غير مرتبطة | 1768 |
| قيود غير متوازنة / غير مرحّلة | 0 / 0 |
| فواتير بمادتين أو أكثر | 1287، منها 1286 فيها أسطر متكررة لنفس الحساب والجهة |
| أنواع الفواتير: bNoEntry / bShortEntry | 1 فقط بلا قيد (bNoEntry)، و bShortEntry=0 لكل الأنواع |

مثال: فاتورة بمادتين ← قيد واحد: سطر مدين للزبون بالإجمالي، وسطران دائنان على حساب الإيراد نفسه (سطر لكل مادة).

## الخلاصة
1. **"قيد منفصل لكل سطر" ليس سلوك الأمين**: قيد واحد لكل مستند، دائماً. تبقى `PerLineJournal` (قيد مستقل لكل سطر) محجوزة ومرفوضة؛ هذا قرار مبني على الدليل.
2. **الفرق الحقيقي هو تفصيل الأسطر داخل القيد الواحد**: الأمين يُصدر سطراً لكل مادة (لا تجميع)، بينما يجمّع الباك إند الإيراد/الحسم/الضريبة حسب (الحساب، مركز الكلفة) في `SqlSalesInvoiceService.Posting.cs` (الأسطر ~342–360) وما يقابله في المشتريات. الأرصدة والإجماليات متطابقة، والاختلاف في عدد صفوف كشف الحساب فقط.
3. لم أغيّر الترحيل: تغيير شكل القيود المرحّلة يمس اختبارات تثبّت عدد الأسطر. المقترح: خيار نمط "تفصيل أسطر القيد" (افتراضه كالأمين: مفصّل) يُنفَّذ كخطوة مستقلة مع اختبارات.
4. أنواع الفواتير ذات `bNoEntry=1` تُنتج بلا قيد؛ يُتحقق أن أنماطنا تسمح بمستند بلا قيد.
